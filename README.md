# CLEARPATH 108

## Phase 3 move-side label policy

Training rows are sampled during seeded simulation runs at approximately two-second
intervals. Up to two same-lane decision vehicles are deterministically sampled per
snapshot, all junction-cross vehicles are retained, and other-lane/oncoming examples
are sampled deterministically per snapshot to keep the dataset manageable. The ambulance starts in a deterministically randomized valid lane for
each road, density, and seed combination.

For same-lane rows, `NONE` means the vehicle is not a slower vehicle ahead of the
ambulance, so no yielding action is currently called for. For a slower same-lane
DECISION row, labels are generated by four separate 10-second joint rollouts: `LEFT`,
`RIGHT`, `HOLD-AND-RETRY` (the runtime `STOP` action), and `NONE`; all other
alerted drivers use the placeholder policy in each rollout. The action that
allows the ambulance to travel farthest during the rollout is selected. A maneuver
may be retried every 0.5 seconds while waiting for its safe gap. Tied outcomes prefer
a currently free adjacent lane, checking driver-left (lane index minus one) before
driver-right; if neither adjacent lane is free, `NONE` is preferred before
`HOLD-AND-RETRY`. Same-lane vehicles that are not slower and ahead, and vehicles in
other lanes, remain `NONE`. Oncoming and junction-cross traffic remain in the dataset
as separate row categories; their metrics are reported separately from DECISION rows.

Runtime `STOP` holds the vehicle at speed 0 in its current lane. It re-evaluates the
selected action every 0.5 seconds and releases when the action is no longer `STOP`;
if a requested lane change becomes unavailable, it keeps moving safely and retries
the action on the next 0.1-second simulation tick, like a placeholder `NONE`. ML
`NONE` responses also remain eligible for next-tick reevaluation. Explicit `STOP`
remains the 0.5-second hold action. The Phase 5 `label-rule-retry` comparison is a separate diagnostic variant:
it replaces `STOP` with cruising at the vehicle's normal safe-following speed and
re-evaluates the label rule every 0.5 seconds.
Data-generation simulations use compliance 1 so action labels describe the selected
action rather than whether a driver complies. Scenario runs continue to use the
simulator's default compliance of 0.88. The regressor feature `slower_ahead_150m`
counts slower same-lane vehicles within 150 m ahead of the ambulance.

Training labels are generated with compliance=1. Scenario runs use compliance=0.88
by default. Training seeds are 1-400, held-out test seeds are 1001-1100, and the
Phase 4 policy comparison uses seeds 2001-2050. These ranges are disjoint; benchmark
seeds are not used for training or validation.

## Production policy

The production CLEARPATH default is a hybrid: placeholder rule-based move-side
actions, with the trained ML corridor-length and ETA models. The UI's CLEARPATH
run button selects this same policy. ETA prediction is display-only and does not
affect vehicle movement or corridor alerts.

The trained ML move-side forest remains available as an experimental policy. It
showed materially worse high-density travel time than placeholder move-side on
seeds 4001-4100, so it is not used by the production default. The model-generated
action labels, rule-based label policy, and mixed policies were also evaluated.
A predicted `STOP` holds a vehicle at zero speed and re-evaluates every 0.5 seconds;
the production placeholder move policy uses its separate safe-gap retry behavior.

All learned models were trained from simulated data. They are not validated for
real traffic, driver behavior, emergency services, or deployment. Simulation
results are comparative evidence only; road geometry, vehicle dynamics, alert
delivery, and compliance are simplified. The corridor forest estimates a
simulated alert horizon and the ETA forest predicts time remaining from simulated
features. Neither is a safety certification or a real-world response recommendation.

## Phase 5 evaluation

Phase 5 retrained and evaluated the move-side forest with rollout-generated
labels, then instrumented lead blockers and retries. The frozen high-density
multilane comparison used compliance 0.88 on seeds 4001-4100. The production
freeze adds a paired baseline-vs-hybrid benchmark at low, medium, and high density
on new seeds 5001-5100, also at compliance 0.88. The production benchmark manifest
records hashes for the simulator inputs, model JSON artifacts and scenario config
before the new seeds are run. Summary metrics are exported to
`web/public/results/benchmark.json` and displayed in the UI Results card.

On seeds 4001-4100, ML move-side averaged 116.11 s travel and 71.26 s blocked,
versus 80.22 s and 20.99 s for placeholder. The recorded placeholder-move plus
ML-corridor hybrid averaged 80.06 s travel and 20.77 s blocked; it strictly beat
placeholder travel on 7/100 seeds (recomputed from the saved per-seed CSV). This
hybrid run used placeholder ETA; ETA is display-only, so the new ML ETA setting
does not alter the recorded travel or blocked results. ML move-side remains in
the repository for experiments, not production.

Run the benchmark from the repository root with `npm run production:freeze`
followed by `npm run production:benchmark`. Configuration and seeds are in
`web/tools/production-benchmark-config.json`; the runner is
`web/tools/production-benchmark.mjs`; the freeze generator is
`web/tools/freeze-production-policy.mjs`; results are written to
`web/public/results/benchmark.json`. The manifest hashes only
`web/src/sim/engine.js`, `web/src/sim/roads.js`, `web/src/sim/features.js`, the
three model JSON files, and the benchmark configuration containing the seed list.
It intentionally does not hash UI files.

The related data and training entry points are `web/tools/generate_dataset.mjs`
(`npm run phase5:generate`) and `ml/train.py` (`python ml/train.py`). Training
rewrites model artifacts, so regenerate the freeze manifest before a new
benchmark after retraining.

The benchmark pairs baseline and CLEARPATH on seeds 5001-5100 with compliance
0.88. That is a simulated driver-response assumption; it is not an empirical
compliance estimate. Clearance improvement percentages omit a paired run when
baseline clearance time is zero; the valid sample count is included in the JSON
and UI. It runs low, medium, and high density on multilane roads,
plus high density on divided and junction roads. Those additional road-type
scenarios are marked unpolished because the simulator policies and road interaction
coverage are less developed there. The JSON stores each paired
seed’s travel time, clearance time, blocked time, alert count and collision
count, along with mean, population standard deviation, median, p10, p90 and
worst-case summaries for each metric. It also stores paired improvement and
strict-win counts.

The latest paired run records mean travel / clearance / blocked seconds and
travel strict wins as follows. Multilane low: 70.10 / 43.09 / 6.05 baseline,
69.72 / 5.13 / 5.34 CLEARPATH, 10/100 wins. Multilane medium: 77.16 / 57.52 /
17.61 baseline, 71.44 / 13.72 / 7.95 CLEARPATH, 67/100 wins. Multilane high:
103.50 / 74.56 / 57.53 baseline, 79.95 / 23.50 / 20.97 CLEARPATH, 92/100 wins.
The divided high-density scenario logged 3,271 baseline and 2,938 CLEARPATH
collision events. Junction high-density logged zero for both. These extra road
scenarios are explicitly marked unpolished in the JSON and UI; the collision
counts show that the model does not yet behave safely on divided roads.

Clearance episodes use the same blocker rule in both modes: a slower, forward
vehicle in the ambulance’s lane and inside that mode’s clearance window starts
an episode; the episode ends when no such blocker remains. Baseline uses a fixed
420 m window. CLEARPATH uses its configured `corridorLen` from the ML corridor model.
`clearanceTime` is the run’s mean duration across its separate episodes.

The Results table is `web/src/components/ResultsTable.jsx`; it compares completed
baseline and CLEARPATH runs for the same road, density, and seed, and clears the
comparison when any of those settings changes. Its benchmark line selects the
matching road and density from `benchmark.json` and reads the seed count and mean
paired improvements from that data. Start the UI from the repository root with
`npm run dev`; create a production build with `npm run build`.

These outcomes only describe the simulator. It assumes simplified traffic,
driver compliance, vehicle speeds, alerts, and road geometry. The multilane
scenarios and junction high-density scenarios logged zero collision events;
the divided test logged many and remains unpolished. Seeded
scenarios are not independent real-world evidence, and zero simulated collisions
does not establish safety. Models and the placeholder policy need external
validation before any real-world use.

When rollout-generated STOP labels are below 1% of main-road DECISION rows, the STOP class is omitted from the move-side forest. The dataset rows remain available for analysis; junction-cross STOP/NONE behavior is handled by an explicit runtime junction rule.

## Phase 6 hospital and status cards

The right side of the ambulance dashboard reports simulated GPS, corridor length,
simulated V2V, and active AI decision status, plus ambulance number, ETA and
simulated route status. Three demonstration hospitals are ranked for Cardiac,
Trauma, or Stroke using a weighted score: 40% ETA, 30% ICU availability, and
30% specialty match. ETA is predicted by the existing ETA model; the ranking
itself is rule-based, not ML. The selected hospital is highlighted. The sample
data intentionally makes the nearest hospital a poor Cardiac choice so that the
specialty and capacity factors affect the ranking. Hospital locations, ETA
inputs, and available ICU beds are simulated data, not live hospital information.
